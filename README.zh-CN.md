# resume_improve_loop

让一组互相独立、带着敌意的评审反复审同一份简历 —— 或其他任何文档 —— 看着分数收敛。

**九位评审在彼此看不见的情况下读同一份文本，各自打分，并逐条引出会让你被刷掉的原句；
你改掉这些句子再跑一轮，直到分数不再变化。**

> **状态：里程碑已封板。** 循环和它的评分契约已经完整，按现状使用；除非项目的输入或
> 目标发生变化，否则不再继续开发。

## 一轮是怎么跑的

```
        ┌─────────────────────────────────────────────────────┐
        │                                                       │
   resume.md ──► 面板中的 N 个 persona（各自独立）──► 评审结果 │
        ▲                                               │       │
        │                                               ▼       │
        └──────────── 应用你接受的修改 ◄──── 汇总 + 分数 ─────────┘
                        （循环到分数进入平台期）
```

一轮就是：为每个 persona 拼一个提示（persona + 简历 + 评分细则），逐条通过 stdin 交给你的
agent 命令行，把回复写进 `runs/round-N/`，从中解析出一个 `score: NN/100`，然后打印一张
按 persona 排列的表格，附均值以及相对上一轮的变化量。当一整轮的均值变化小于
`--plateau` 时就可以停了 —— 再跑下去只是白费。

## 快速开始

`loop.py` 只用 Python 3.10+ 标准库，不需要安装任何东西。

```sh
# 1. 任选一个"从 stdin 读提示、往 stdout 写回复"的命令行工具。
export RESUME_LOOP_AGENT="claude -p"     # 或者 "pi -p"、"llm -m gpt-4o-mini"

# 2. 审仓库自带的虚构简历；结果落在 runs/round-1/
python3 loop.py --resume examples/resume.sample.md --rounds 1

# 3. 读 runs/round-1/DIGEST.md，应用你接受的修改，再跑一轮
#    （round-n 按输出目录里已有的轮次接着编号）。
python3 loop.py --resume examples/resume.sample.md

# 只对磁盘上已有的结果重新打分，不调用任何 agent：
python3 loop.py --aggregate-only
```

想先看提示、不想花 token？`python3 loop.py --resume myresume.md --dry-run`
只打印拼好的提示，不调用任何人。

## 现在能做什么

- **开箱九种 persona**：ATS 解析器、HR 初筛、用人经理、领域研究员、创业公司负责人、
  猎头、海外 HR、HRBP，以及一位专门唱反调、认为其他评审低估了候选人的"弱信号辩护人"。
- **每位评审每轮一个分数**，从 `score: NN/100` 解析（也接受中文写法
  `约面概率(0-100)：NN` 和裸写的 `45/100`），并给出按 persona 的趋势表和最近两轮的差值。
- **只引原句、不许转述**的 red flag —— 每条问题都指向一行你可以直接改的字。
- **自检尾巴**（`Correct` / `Finding` / `Merge verdict`），强制每个 persona 区分角色扮演的
  主观判断和可核查的事实陈述。
- **有边界、会重试的运行**：并发池（`--jobs`，默认 2）、单次超时（`--timeout`，默认 600 秒）、
  失败的评审员被塞回队尾重试（`--retries`，默认 2），而不是立刻再撞一次限流。
- **每轮一份汇总**（`runs/round-N/DIGEST.md`），以及 `--personas` 让你只调某一位评审。
- **运行产物留在本地**：`runs/` 里是你的简历原文，默认被 git 忽略。

## 评审契约

每个 persona 都必须以一段机器可读的块结尾，驱动才能给它打分（完整规格见
[`RUBRIC.md`](RUBRIC.md)）：

```
## Score
score: 62/100

## Red flags
1. "<原样引用的句子>" —— 为什么这句话会伤人
...

## Most fatal line
> <你只会念出来当作淘汰理由的那一句>

## Verdict
一段话，不要和稀泥
```

后面再跟一个简短的自检尾巴：

```
## Review
- Correct: 这个 persona 正面核实了什么
- Finding: 上面哪些是角色扮演的观点、哪些是事实主张（要标出来）
- Merge verdict: 你的建议
```

`Finding` 这一行是关键：persona 被允许"故意说错"（一个刻薄的招聘官），但它必须承认这一点，
而不是把观点包装成审计结论。

## 为什么用面板，而不是一次评审

- **不同的岗位因不同的原因拒绝。** ATS 解析死格式；招聘官死在十秒扫读；用人经理死在内容
  是空的；海外评审死在本地人默认你懂、其实没写的背景。
- **独立性限制共同的盲区。** 一个评审的口味会变成全部分数；一组人能把分歧摆到台面上。
- **分数要看趋势，不能看单点。** 每轮用同一套细则；不再变化的分数才是真正的终点线。

目的不是让评审满意，而是让你用自己的话看清：一个不友好的读者会拿哪几行来质问你。

## 架构

```
loop.py                 驱动：拼提示、跑 persona、重试、汇总、判平台期
RUBRIC.md               评分维度，以及每个 persona 必须遵守的输出契约
personas/*.md           九个评审，一人一个文件，用文件名主干来选取
examples/               一份虚构简历，和一轮完整的示例评审
docs/METHOD.md          设计理由，以及七轮真实运行得到的经验
tests/test_loop.py      标准库冒烟测试：打分解析、提示拼接、persona 加载
assets/logo.svg         图标
```

可执行代码只有 `loop.py` 一个文件。它读一次评分细则，把它附到每个提示后面，并把每一份
persona 当成不透明的提示文件 —— 面板是数据，不是代码，所以加一个评审就是加一个 Markdown
文件。驱动对一次评审的全部认知都从 stdout 回来：回复正文，以及从中解析出的一个分数。
每一轮就是普通目录（`runs/round-N/`），所以重新打分或对比旧轮次既不需要数据库，也不需要
agent。

设计理由 —— 为什么输出契约才是关键、怎么给意见分诊、七轮跑下来学到了什么 —— 都在
[`docs/METHOD.md`](docs/METHOD.md)。

## 开发

```sh
# 冒烟测试（标准库，无依赖）：
python3 tests/test_loop.py

# 如果你装了 pytest，也可以：
python3 -m pytest tests/ -q
```

没有构建步骤，也没有 lint 配置；整个程序就是 `loop.py`。改打分或提示拼接时，请在
`tests/test_loop.py` 里补一条断言 —— 那是解析器的回归网。

## 路线图

**已实现**

- 九种 persona、评分契约和自检尾巴。
- 并行驱动：失败重排、单次超时、平台期自动停止。
- 分数表、每轮汇总、`--aggregate-only`、`--dry-run`、按 persona 选取。
- 一轮完整的示例，以及一份写下来的方法论。

**计划中**

- 没有承诺项。项目是一个已封板的里程碑；欢迎能让 persona 更准、或让解析器更宽容的
  issue，但没有一份许诺功能的路线图。

这件事指向哪里：这个循环是文本优化器，七轮跑下来每次都得到同一个结论 —— 当措辞不再让
分数移动时，下一步的改进来自做出一个可核查的产物，而不是再改一遍措辞。把这一步一般化
（从"指出弱的那一行"到"指出能修好它的证据"）是有意思的方向，留给真正需要它的人。
